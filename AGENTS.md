# Working in paperclip-company-standards

You are an agent making changes in the repo that thirteen Paperclip companies configure themselves from. This file tells you how to work here. Read it before editing.

Treat these as **good defaults, not hard rules**. The person directing you can override anything here, and their intent wins.

## Read these two first

This repo already carries the orientation material, so it is not repeated here:

- **[`CONTEXT.md`](./CONTEXT.md)** — the glossary. Every term used across the standards: company tiers, agent roles, role packs, VISION/SOUL, the quality-gate concepts. Read it before any other doc; the standards are unreadable without it.
- **[`SOURCE_MAP.md`](./SOURCE_MAP.md)** — the read order, section by section.

What follows is what those two do not cover: what this repo is *for*, what it must never become, and how changes go wrong here specifically.

## Two different files are called AGENTS.md — do not confuse them

| | |
|---|---|
| **This file** | The guide for an agent working **in this repo**. Hand-written, version controlled here |
| **Company AGENTS.md** | Generated by `standards/sync-bootstrap.sh` from `roles/_shared/` plus a role pack, and written to `~/Docs/paperclipcompanies/<company-slug>/AGENTS.md`. It is the guide for an agent working **inside a company** |

The script never writes to this repo's own `AGENTS.md`, so editing this file is safe. But when a task says "update AGENTS.md", establish which one is meant before touching anything — they have different audiences and opposite lifecycles: this one is edited by hand, that one is regenerated and any manual edit to it is lost on the next sync.

## What this repo is

The canonical standard for how a Paperclip company is built and run — roles, models, stack, flows, bootstrap configs, and the role packs distributed by `standards/sync-bootstrap.sh`.

**Its output is not documentation. Its output is configuration.** Thirteen central companies plus one game company per active title read this repo and configure their agents from it. A wrong model id here does not produce a confusing paragraph; it produces agents that fail to start.

That has happened. `CONTEXT.md` records it in one line: a `latest` alias used as a model id was an invalid identifier and **stopped Product Design for five weeks**.

## What must never happen here

**The same fact in two places.** This is the failure mode this repo has actually suffered, repeatedly. Of five errors made on 2026-07-29, three were this exact class — `docs/` disagreeing with `CHANGELOG.md`, a PR title disagreeing with its own body. The `.github/workflows/consistency.yml` check exists because of it and verifies JSON validity, shell syntax, semver fields, and CHANGELOG↔tag drift.

Before adding a fact, find where it already lives and edit that. When a fact genuinely must appear twice, make one of them the source and have the other point at it.

**A standard nobody runs.** Every "Validation check" in `docs/stack-standard.md` was prose — an instruction for a person to run by hand — and nobody ran them. `gstack` sat listed as **required** and was never installed on the reference machine. `scripts/validate-stack.sh` exists to make the standard executable; keep it that way. **A checker nobody runs is not a check**, and prose that describes a check is not a checker.

**A manifest pointing at things that no longer exist.** `config/skills-manifest.json` is what twelve companies configure their Codex workers from. It listed two skills that had been renamed or removed upstream months earlier. When you reference anything external, verify it still exists — and record the date and source you verified against.

## Three ways to hurt yourself here

**1. Editing a role pack without thinking about distribution.** Files under `roles/` are pushed to live agents by `standards/sync-bootstrap.sh`. A change here reaches running companies. There is no staging tier between this repo and production.

**2. Writing a standard that cannot be checked.** If a new rule cannot be expressed as something `validate-stack.sh` or the consistency workflow can test, it will drift and nobody will notice for months. Prefer a rule you can verify over a rule that reads well.

**3. Assuming the design is the problem when the system is simply not running.** On 2026-08-13 the Knowledge company had produced nothing for fifteen days. Every agent in it — CEO, Librarian, Tracker, Auditor — was in `error` or `paused` after a server restart, and nothing alarmed. A daily routine kept creating issues into a dead company and reported success each morning, because its precondition checked whether the *server* was up and never whether the *agents* were. Before changing an orchestration standard because it "isn't working", check whether the agents are alive.

## Before you call it done

- **CHANGELOG** — user-visible changes get an entry. The consistency workflow checks CHANGELOG↔tag drift and will fail the build.
- **Version fields** — `config/*.json` version fields must be semver. `latest` and other aliases are not version identifiers and have broken production here.
- **SOURCE_MAP** — a new document needs an entry, in the right section.
- **known-issues** — if the work resolves a `KI-PS-*`, mark it resolved with the date and the deciding authority.
- **Both directions of a cross-reference** — if `docs/x.md` now points at `roles/y/README.md`, check whether `y` should point back.
- **`validate-stack.sh` still passes**, and if the change adds a requirement, that the script actually tests it.
- **Consistency workflow green** — it runs on every push and catches the drift class this repo is prone to.

## A note on how we work

This repo is read by machines that cannot ask a clarifying question. An ambiguity here does not become a message; it becomes thirteen companies configured slightly differently, discovered weeks later.

So prefer the precise sentence over the elegant one, state what a value must be rather than what it should generally look like, and when something is genuinely undecided say so in `docs/known-issues.md` rather than writing a plausible-sounding rule that nobody has actually agreed.
